## Fact views

Raw tables (001_tables.sql): `introspection.spans` (:7), `logs` (:28), `session_projects` (:51), `hook_events` (:71), `prompt_labels` (:89). Everything the dashboard reads is derived from these; the tables are loaded by refreshable materialized views (APPEND) from SigNoz `signoz_traces.distributed_signoz_index_v3` (select_spans.sql:112) and `signoz_logs.distributed_logs_v2` (select_logs.sql:206), filtered to service names `codex-app-server`, `codex_cli_rs`, `codex_exec`, `oh-my-pi`, `claude-code` (select_spans.sql:113, select_logs.sql:207). Loaders (facts.py:56-95): `load_spans` every 1 minute (spans started within 1 day and ending within 30 min), `sweep_spans` hourly (90 days / ended within 3 days), `load_logs` every 1 minute (observed within 30 min, event within 7 days), `sweep_logs` hourly (3 days).

Snapshot set (facts.py:130-137): usage*events, task_outcomes, tool_calls, user_signals, model_calls, task_labels. Each has table `introspection.<view>_snapshot` (MergeTree) refilled by `refresh*<view>`materialized view`REFRESH EVERY 1 MINUTE DEPENDS ON load_spans, load_logs`(facts.py:198-217), reading the view with spans/logs bounded to`ts >= now64(9) - 91 DAY` (facts.py:115-118). Non-snapshot views (session_project, hook_rows, hook_tool_calls) are always live.

Privacy stripping at extraction (applies to the raw tables, hence every view):

- Spans (select_spans.sql): drops attribute keys `gen_ai.tool.description`, `user_prompt`, `prompt`, `user.email`, `user.account_id`, `user.account_uuid`, `user.id`, `organization.id`, and any `*.tool.call.intent` (:97-100); span name redacts `/Users/<name>` to `~` (:46); status message reduced to the single most diagnostic line, secrets redacted, 20+ char tokens bracketed/redacted, digit/hex runs to `N`, capped at 80 chars, plus `x.status_hash` (16 hex SHA-256) (:11-110). `pi.gen_ai.*`/`omp.gen_ai.*` attribute prefixes are unified to `pi.gen_ai.*` (:92-110). Codex spans kept only for names `session_task.turn`, `session_task.run`, `run_sampling_request`, `try_run_sampling_request`, `turn/start`, `turn/interrupt`, `turn/steer` and `handle_responses` with token usage (:113-121).
- Logs (select_logs.sql): drops `prompt`, `arguments`, `output`, `content`, identity keys (:113-116); Codex tool results get derived `x.command_head`, `x.command_sub` (only for a fixed list of subcommand tools), `x.gate_bypass`, `x.workdir` (home -> ~), `x.targets` (max 20, paths only), `x.arguments_hash`, `x.failure_signature` (normalised, 80 chars) + `x.failure_signature_hash`, `x.exit_code`, lengths (:97-203).
- Pipeline `pipeline.sanitization` signal counts rows that still hold a dropped key, a status message over 160 chars, or a home path (expected 0) (signal_support.toml:376-382).

## Snapshot and window rules

- Windows: every view query binds `{start:DateTime64(3,'UTC')}`, `{end:DateTime64(3,'UTC')}`, `{harness:String}` as ClickHouse parameters (`dashboard/server/views.ts:22-23,29-37`; params bound by `clickhouse.ts:122-123`). Window is `ts >= start AND ts < end` (half-open, UTC instants) on the view's time column (`ts` or `start_ts`) plus `HARNESS_FILTER`.
- `HARNESS_FILTER` (`views.ts:28-30`): `harness IN (SELECT harness FROM introspection.harnesses WHERE enabled = 1) AND ({harness:String} = '' OR harness = {harness:String})`. So "All" = union of the harnesses this machine enables (not all five), and a selected harness is further limited to enabled ones. `inWindowOf(alias, ts)` (:36-37) applies the same to a joined alias. Asserted by `server.test.ts:601-610`.
- Snapshot vs live (`server.ts:377-396`): `withinSnapshots = start >= now - (SNAPSHOT_DAYS+1) days` (SNAPSHOT_DAYS = 90, `clickhouse.ts:141-142`). If true the `*_snapshot` tables are queried; otherwise `live()` (`clickhouse.ts:148-154`) rewrites `introspection.<x>_snapshot` to the live view `introspection.<x>`. Session queries always use `live()` (`server.ts:434-435`: a session can be older than the snapshot horizon). Pipeline receives `withinSnapshots` too (`server.ts:385`).
- Snapshot horizon: snapshot refresh bounds spans/logs to 91 days (`facts.py:115`); sweeps rebuild up to 90 days of spans and 3 days of logs (facts.py:70-83); SigNoz retention is 90 days (facts.py:110).
- One request per view: `batch()` (`clickhouse.ts:163-186`) UNION ALLs every named dataset into a single HTTP request; every statement runs `readonly=2` with `max_execution_time` = QUERY_TIMEOUT_MS (:116-121).
- Time zones: window instants are UTC; day buckets are mostly `toDate(ts)` (server time zone of ClickHouse; unqualified, in V2, V3, V4, V5, V6, V7 daily queries, `views.ts:135,159,184,233,269,320`); `toDate(ts, 'Europe/London')` is used for failure-cluster days (`views.ts:82,88`), recurrence `targets` days (:337), recurrence `daily` (:365), interventions `cluster_daily`, `correction_daily`, `task_daily` (:413-425) and `LONDON_WEEK_OF` = seven London calendar days ending on the window end (`views.ts:125-127`, used by actionable repeats). Browser side `londonDay()` (`Interventions.tsx:23-27`) formats instants in Europe/London to match. Pipeline displays parity window as `... UTC` (`Pipeline.tsx:138-139`). Parity window is `[greatest(start, end-7d), least(end, now-10min))` (`pipeline.ts:414-416`).
- Evaluation workspaces are excluded (project root / failure signature matches `EVALUATION_PATH`) from failure clusters and repeated corrections (`views.ts:69-70,405`).
- Python detectors (findings, evaluation, evidence) use `enabled_filter` and snapshot tables: `findings.py:77-103` (7 London days), `evaluation.py:94-96` chooses snapshot when the window starts within 90 days.
